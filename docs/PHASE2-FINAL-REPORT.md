# Custom Product Designer — Phase 2 Final Report

**Repository:** `kamandbeauty/Ideal` · branch `arena/01a06d64-ideal`
**Plugin version:** 1.1.0 (DB schema 1.1.0)
**Report date:** 2026-09-05
**Verdict:** **NOT READY FOR PRODUCTION** — see §22.

---

## 1. Scope and what was actually built

Phase 2 turned a t-shirt-only 3D designer into a product-type-driven custom
product platform, and connected it to a complete WooCommerce sales cycle.

| | Phase 1 | Phase 2 |
|---|---|---|
| Product types | t-shirt only, hard-coded | registry-driven, `tshirt` + `totebag` shipped |
| Design identity | row id | UUID + version + ownership |
| Sales cycle | designer only | Product → Customize → Save → Price → Cart → Checkout → Order → Production files → Admin |
| Text | none | full text tool, re-rendered at print DPI |
| Admin | CRUD screens | production panel, ZIP export, regenerate, design library |
| Automated tests | 35 unit | 463 across 4 suites |

62 PHP files, 9 designer ES modules, 11 database tables.

## 2. Architecture rename

The plugin now presents as **Custom Product Designer** throughout the UI, the
admin menu and the v2 REST namespace. The internal `tshirt-designer` slug,
`TShirtDesigner\` namespace, `td_` table prefix and text domain were
deliberately **kept**: they are the plugin folder name, the option keys and the
translation domain of a plugin already carrying live Phase 1 data. Renaming
them buys nothing a customer can see and risks orphaning existing rows.

## 3. Product type extensibility

`Product_Type_Registry` owns the type definitions and exposes the
`cpd_product_types` filter. A type declares its label, allowed print-area
types, whether it has sizes, and its default print DPI. Models, colors, sizes,
print areas, pricing rules and production settings all hang off the type.

Adding a hoodie, cap, mug or phone case is a filter callback plus content — no
Core change. This was verified by the tote bag, which was added through the
same path and required no edits to the designer, pricing engine, cart, order
or production code.

**Not every product has sizes**: the tote ships with a single "One size" row
and the size surcharge resolves to zero rather than erroring.

## 4. Print areas

T-shirt: FRONT, BACK, LEFT_SLEEVE, RIGHT_SLEEVE. Tote bag: FRONT, BACK.

Sides are independent — each holds its own item list, and a side with no items
produces no print file. Multiple items per side are supported (cap 20).
Maximum width/height are **admin-configurable per area** (clamped 0.5–200 cm),
seeded at 30×35 cm for the shirt body and 28×32 cm for the tote; nothing is
hard-coded. Each area carries a UV rect, so artwork is composited into the
model's texture and follows the fabric when the model rotates.

## 5. Models

Multiple models per type, each with its own GLB, base price, colors, sizes and
print areas. Shipped: Classic T-Shirt (350,000) and Classic Tote Bag
(220,000). The tote GLB is generated by `tools/generate_totebag_model.py`
(4,856 triangles) with UV rects matching the seeded print areas.

## 6. Design identity, versioning and ownership

- **UUID** per design, format `DESIGN-8F72A91`.
- **Versioning**: every save writes a new row in `design_versions` holding the
  full design JSON and its own immutable price snapshot. An order binds to the
  exact version purchased.
- **Ownership**: user id, or a secure guest token stored in an HttpOnly
  `td_guest` cookie (30 days). On login `claim_guest_designs()` migrates guest
  designs to the account.
- **Restore / duplicate / delete** all implemented and ownership-checked.

## 7. My Account → My Designs

Endpoint `my-designs` with view, edit, duplicate, delete and **order again**.
Order-again duplicates first and carts the copy, because an ordered design is
immutable — re-carting the original would let a customer edit the record of a
completed sale. Designs attached to an order cannot be deleted.

## 8. Previews

A preview image is captured from the 3D viewer at save time and reused in the
designer, My Designs, cart, order and admin. Stored as a media attachment, so
WordPress handles the sizes and CDN offloading.

## 9. Production files

Generated **per area, only where the customer actually designed**. Resolution
is physical size × DPI, with DPI settable globally and per product type
(clamped 72–1200). Transparent PNG is preserved, layer order is respected, and
text is re-rendered from its stored data with the real TTF rather than being
upscaled from the preview bitmap.

Naming: `ORDER-1001-DESIGN-A123-FRONT.png` (sleeves become `LEFT-SLEEVE`).
ZIPs are `ORDER-<id>-PRINT-FILES.zip`, or `...ITEM-<item_id>...` per line.

Files live in a protected directory with `.htaccess` and `index.html`, and are
served only through a capability- and nonce-checked admin-post endpoint with a
realpath containment check.

## 10. Pricing

Server-authoritative and layered: base + size modifier + per-area print charge
+ size tier + item count. Per-area rules override global ones, so front and
back price independently.

The browser never sends a price — the cart route accepts only a design id and
a quantity. A price snapshot is stored at save and again at add-to-cart, and
changing a rule afterwards provably does not alter past orders (covered by
test).

## 11. WooCommerce integration

Standard hooks and public API only: `woocommerce_add_cart_item_data`,
`woocommerce_get_item_data`, `woocommerce_before_calculate_totals`,
`woocommerce_checkout_create_order_line_item`, `woocommerce_payment_complete`.
No core override, no template hijack, no custom payment gateway. Cart data
survives refresh and checkout via the session. Order item meta carries the
design code, model, color, size, version, product type, preview, pricing and
the full snapshot. The snapshot is immutable once the order exists.

Tested against **WooCommerce 9.4.2** on **WordPress 6.9**.

## 12. Admin

- **Order design panel** (legacy metabox and HPOS): preview, model/color/size,
  per-area print sizes, item counts, DPI, price breakdown as charged, per-area
  downloads, Download All ZIP, regenerate-from-snapshot, production status.
- **Design library**: search by code or id, filters for product type, model,
  status, user, order and date range, pagination.
- **Product types screen**: what each type owns, plus per-type DPI with a live
  "a 30×35 cm print becomes N×M px" hint.
- RTL-aware and responsive down to 782 px.

Regenerate reads the **order snapshot**, not live data — verified by a test
that shrinks the print area and changes the base price, then regenerates and
confirms the purchased dimensions come back.

## 13. Security

Nonces on every form and action link; `permission_callback` on all 15 REST
routes; ownership re-checked on every design read and write; `manage_options`
on admin actions. All input sanitized, all output escaped. All SQL goes
through `$wpdb->prepare()`; a SQL injection attempt through the admin search
box is a test case.

Uploads validate MIME, extension and size, honour `proper_filename`, and are
rate-limited (20/hour default). Only jpg/jpeg/png/webp are accepted. **SVG is
rejected** — it is not accepted at all rather than shipped with a sanitizer of
uncertain coverage.

Two IDOR vulnerabilities found in Phase 1 code were fixed during this work.

## 14. File lifecycle

Draft → Saved → Ordered → Paid → Production. The daily cleanup job deletes
only stale draft/saved guest designs; it skips anything in a protected status
and anything referenced by a production file row, and it never deletes
production files. Verified by test.

## 15. Database

11 tables, all `td_` prefixed. Migrations run through `Migrations::steps()`
keyed by version; the 1.1.0 step adds product types and versioning
**additively** — no column is dropped or retyped, and Phase 1 data keeps
working. 45 indexes; foreign keys are logical (InnoDB constraints are avoided
because WordPress hosting cannot be relied on for them).

## 16. Front-end designer

3D viewer with texture-composited artwork, a physical-centimetre 2D print-area
editor with move/resize/rotate, layers, uploads, an asset library, a text tool
and a live server-priced total.

Four real defects were fixed here in this phase: layer order was ignored in
both renderers and never sent to the server; item opacity was stored but never
drawn; the editor repainted every animation frame forever, pinning a CPU core;
and the designer was hard-coded to `dir="ltr"`.

## 17. Text

Text is stored as **structured data** — content, font, colour, weight, style,
alignment, direction — never as a flattened bitmap. It stays editable, and the
print file is rendered server-side with the real TTF at full print resolution.
Four fonts ship, including Vazirmatn for Persian. Direction is auto-detected
from the content and can be overridden.

## 18. Mobile and RTL

Tools collapse into a drawer under 980 px; 44 px touch targets; chip rows
scroll rather than wrap; the price is sticky; 16 px inputs stop iOS Safari
zooming on focus; `prefers-reduced-motion` respected. The app root follows
`is_rtl()`, while the print editor stays LTR because its coordinates are
physical centimetres from the print area's top-left corner — mirroring it
would move artwork to the wrong side of the garment.

## 19. Performance

Textures composited into a single 2048² atlas; images loaded once and cached;
repaints coalesced into one animation frame; previews cached as attachments;
production file generation deferred to a scheduled single event so payment
completion does not block on rendering.

## 20. Error handling

Missing model, colour, size, area, asset, upload, pricing rule or WooCommerce
all degrade to a message rather than a fatal. The cart route returns 501 when
WooCommerce is absent, and the Add to Cart button is not rendered at all.

## 22. Production readiness verdict

### NOT READY FOR PRODUCTION

The code is functionally complete against the contract and 463 automated tests
pass against real WordPress and WooCommerce. What is missing is not features —
it is **evidence from a real environment**. Everything above was verified
under php-wasm with an SQLite database and a headless test harness. No human
has opened the designer in a browser, no GPU has rendered the GLB, no printer
has received a production file, and no real payment has been taken.

Shipping to a live shop on that basis would be a guess.

### Remaining items

#### Critical — must be resolved before launch

1. **No browser verification of the designer.** The 3D viewer, texture
   compositor, 2D editor, text rasteriser, drag/resize/rotate and the
   Add-to-Cart flow have never executed in a real browser. The JS is
   syntax-checked and logic-tested where testable from Node, but WebGL,
   `canvas.toDataURL`, pointer capture and font rendering cannot be verified
   that way. Needs a manual pass on desktop Chrome, Safari and at least one
   real Android and iOS device.
2. **No MySQL verification.** All database work was tested on SQLite via the
   WordPress SQLite integration layer. Collation, `utf8mb4` behaviour with
   Persian text, index effectiveness and `dbDelta` behaviour on a real MySQL
   or MariaDB server are unverified.
3. **No real payment run.** `payment_complete` is exercised with the COD
   gateway in tests. A real gateway's ordering and timing around
   `woocommerce_payment_complete` must be confirmed on staging.
4. **Print output has never been printed.** The production PNGs are correct in
   pixel dimensions, transparency and layer order, but no print shop has
   confirmed that the colour handling and DPI meet their requirements. Get one
   physical proof of each product type before selling.

#### High

5. **Migration rehearsal on a copy of live Phase 1 data.** The 1.1.0 migration
   is additive and tested on fresh installs and synthetic Phase 1 rows, not on
   a real production dataset.
6. **Load and concurrency.** Production file generation, ZIP building and
   texture composition have not been tested under concurrent orders. The
   scheduled-event approach should be re-examined on a busy shop; Action
   Scheduler would be the natural upgrade.
7. **No product-type switcher in the designer UI.** The backend supports many
   types and the tote is fully functional, but the designer lists models
   without letting a customer switch product type. Reachable today only by
   linking to a specific model.
8. **Capability model is coarse.** Everything admin-side requires
   `manage_options`. A production operator who should only download print
   files and move statuses currently needs full administrator rights.

#### Medium

9. Guest-token cookie lifetime (30 days) and the cleanup retention window
   should be confirmed against the shop's actual policy.
10. Uninstall currently preserves data unless explicitly opted out. Confirm
    that matches expectations.
11. No admin-side bulk operations across orders (e.g. download all print files
    for today's orders in one action).
12. The asset library has no admin-side bulk upload.
13. Accessibility has not been audited: keyboard-only operation of the 2D
    editor and screen-reader labelling of the layer list are untested.

#### Low

14. `tools/make_translations.py` still lists three unused Persian entries from
    Phase 1.
15. No `readme.txt` in WordPress.org format.
16. The plugin folder and internal namespace still say `tshirt-designer` (see
    §2 — a deliberate decision, but worth revisiting if the data can be
    migrated safely).
17. Draco compression is not applied to the GLB files; both models are small
    enough today that it does not matter.

### Recommended path to READY

Work items 1–4, then rehearse 5 on a staging clone of the live site. Items 7
and 8 are worth doing before launch if the shop intends to sell tote bags from
day one or to give a print operator admin access. Everything else can follow
a first release.
