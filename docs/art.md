# Art — the pipeline, the contract, and the brief

The acceptance criterion for this project is blunt: **the graphics must look professional, at the level
of the source game**. M3 built the engineering around that — the contract, the import rules, the
placeholder fallbacks, the gates — and then drew the set with our own generator, from our own palette,
in the flat-vector direction the brand sheet already chose (§6). Nothing is generated by a model, and
nothing is borrowed.

So the set is real: 43 files, exact sizes, validated on every push, and `--strict` is green. It is also
not the end state. The honest claim today is narrower, and it is stated in §7: the structure, the
colour and the silhouettes are deliberate; the light is flat, and `home_palace` wants a painter.

## 1. How art enters the game

```
art/manifest.json                     the contract: id, size, group, required, description, brief
        │  tools/art/art.py --emit
        ▼
Assets/Game/ArtCatalog.gen.cs         generated: the ids the code may ask for
        │
        │  artist exports PNG                          ┌──────────────────────────────┐
        ▼                                             │ missing? → token placeholder │
Assets/Game/Resources/art/<id>.png ──▶ ArtLibrary.Get(id) │ wrong size? → CI fails       │
        │  ArtImportSettings (editor)                  └──────────────────────────────┘
        ▼
SpriteRenderer / Image               screens draw art when it exists, tokens when it does not
```

Three properties fall out of that shape, and they are the reason it is worth the indirection:

- **Art is additive.** A screen never depends on a file existing, so art can arrive one sprite a week
  without a branch, a flag or a broken build.
- **The contract is checked twice.** CI validates the manifest and any committed PNG; the editor
  importer logs when an imported file is the wrong size or is not in the manifest at all.
- **The ids live in one place.** `ArtCatalog.gen.cs` is generated; a rename in the manifest regenerates
  it, and `ArtCatalogTests` fails if the engine grows a piece or an obstacle that the contract does not
  describe.

## 2. Rules the contract enforces

| rule | why |
| --- | --- |
| PNG, with a real alpha channel | Everything composites over a board and a palace plate; a baked background cannot |
| Width and height multiples of 4 | ASTC/ETC block compression needs it; a 830 px plate silently becomes a 832 px blur |
| ≤ 2048 px per side, ≤ 1 MB per file | The install budget is 150 MB and the texture budget is what GPUs actually charge |
| Sprites, not textures | `ArtImportSettings` sets it on import so nobody has to remember |
| No baked text | It cannot be translated, scaled, read by accessibility, or flipped for RTL |
| An id, a size, a description **and** a brief for every entry | An asset without a brief is a guess that gets drawn twice |

```bash
python3 tools/art/art.py                 # report: contract, catalog, what exists, what is missing
python3 tools/art/art.py --emit          # regenerate ArtCatalog.gen.cs
python3 tools/art/art.py --check         # CI: contract valid, catalog current, existing files valid
python3 tools/art/art.py --check --strict  # release gate: every required asset exists and is valid
```

Today: **43 assets in the contract, 43 on disk, 10 required — all present.** They are produced by
`python3 tools/art/gen_art.py` and must match it byte for byte (`gen_art.py --check`). The placeholder
path still exists and is still tested: delete any PNG and the screen falls back to token colours
instead of breaking, which is what makes art additive.

## 4. The brief

The full per-asset brief is in `art/manifest.json` — the same file CI validates, so it cannot drift
from what the game asks for. The visual direction is `replica/design/art-direction.md`: Persian-royal,
lapis night and turquoise enamel, gold for reward, ivory type; muqarnas, brick, cypress, tile; no
characters, no Disney.

The four rules that decide whether a set looks like a game or like a mockup:

1. **Silhouette first.** All five stones must be distinguishable in greyscale at 48 px, because that is
   the size they are actually played at. Shape, then colour.
2. **One light, one camera.** The three district plates share a light direction and a horizon, so
   building a district reads as the same place changing.
3. **No baked effects.** Glows, particles, damage states, tints and 9-slice scaling happen in code
   (`BoardScreen`, `UiKit`); a baked glow cannot be animated, tinted or reused.
4. **Respect the layout.** The home plate leaves its left third calm for the level card; the board
   frame must not compete with the pieces. The layout is `docs/ui.md` §3 and it does not bend for art.

## 5. Review gates

- `art.py --check` in CI on every push; `--strict` before a store build.
- `gen_art.py --check` in CI: a committed PNG that no longer matches the generator is a diff nobody
  reviewed, so it fails.
- `preview.py --check` in CI: the five stones are compared as 48 px greyscale outlines and the job
  fails if any two are the same shape in practice. `preview.py` also writes the review sheet
  (`art/preview/index.html`, images inlined) that a human looks at.
- `ArtTools → Report missing art` in the editor for the artist's own loop.
- A `_PersianCheck`-style visual pass is **not** enough: every sprite is checked for size and alpha in
  the file itself, and the board is checked at 48 px and at cell size.
- The performance gate is unchanged: 60 fps on a Redmi Note 10, ≤ 150 draw calls, ≤ 150 MB install. The
  board is one texture per piece kind, so batching depends on keeping the pieces in one atlas — that is
  the next pipeline step once the art exists (Sprite Atlas per group, added to `ArtImportSettings`).

## 6. Why the art is drawn in code, and why nothing "generated" ships

The user asked for graphics at the level of the original, and also accepted the clean-room rule that
we never ship the original's assets. AI-generated imagery satisfies neither: it is not authored to a
style guide, it cannot be iterated by an artist, and every model's output carries provenance we cannot
state in a store listing. Concepts live in `replica/design/concepts/` as reference only.

So the shipped set is **drawn by our own tool**: `tools/art/gen_art.py`, on top of `tools/art/draw.py`,
from the palette in `replica/design/tokens.json`. That is a deliberate choice, not a placeholder
shortcut:

- it is ours, so the licence question does not exist;
- it is code, so it is reviewable in a diff, reproducible byte for byte, and changeable in one line
  (`--check` fails if a PNG drifts from the generator);
- it is flat-vector, which is the direction the brand sheet already chose, and it survives being
  shown at 48 px;
- an artist can still replace any single PNG without touching anything else — the file *is* the
  contract.

What it is not: a commissioned art pass. There are no painted textures, no baked lighting, no
character work, and the scenes are composed from the same shapes as the sprites. `docs/art.md` §7
lists exactly what a human should replace first, so nobody mistakes this for finished art direction.

## 7. What is drawn, and what a human should replace first

All 51 assets in the contract exist, at the exact sizes the manifest asks for; `art.py --check
--strict` is green. The set was drawn in this order of care:

1. **The five stones** — one bezel language, five silhouettes that survive 48 px and greyscale
   (`tools/art/preview.py --check` measures the outlines and fails if two of them collide).
2. **The HUD icons and the four obstacles** that sit on top of a stone.
3. **`home_palace`** — a moonlit courtyard: facade, iwan with muqarnas, tiled dome on a drum, two
   minarets, a studded door, a reflecting pool, cypresses. The visual weight is right of centre; the
   left third stays calm for the level card, as the brief asks.
4. **The three district plates** — one camera, one light, one palette, so "built" reads as progress.
5. **The twelve task props, the chest, the nine-slice frames and the app icon.**
6. **The two result plaques and the moves icon** — one silhouette in two moods: gold keyline and a warm
   halo for a win, silver and a crescent for a loss. The middle of the plate is deliberately quiet,
   because the title, the three stars and the reward are drawn over it in code.
7. **The five settings icons** — one silhouette each, checked at 22 px, where a cog would be a smudge
   and a phone with wide rings read as a mug.
8. **Still to draw** (each one goes in the manifest before it is drawn): the open chest state, the gate
   states for a built district, the level-node markers on the map, the in-level booster icons, the
   task-card frame, and the day/night plate variants.

Left for a human artist, in the order that would improve the game most:

- **`home_palace`**: the strongest asset in the set and still the weakest thing on the home screen at
  full size. It wants painted light (a glow behind the gate, dust in the air) that a vector generator
  cannot honestly fake.
- **The district plates**: they are stage sets, not paintings. The arches read, the ground does not.
- **`reward_chest`**: one closed sprite. The open state is a tint/scale in code today; it wants a
  second drawing.
- **The result plaques**: they are ornaments, not illustration. A win screen wants the palace lit up
  behind the card, which is a painted asset and not a garnish.
- **`prop_ch01_gate`**: drawn closed only; the "built" plate needs the open state.
- **No animation**: idle, swap, cascade and chest reveal all remain unimplemented. The motion tokens
  exist; the clips do not.
- **No atlas**: 51 sprites is small enough to let Unity pack them, and doing it by hand now would
  cost more than it saves.
